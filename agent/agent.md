- Когда я пишу в тебя запрос помочь с чем-то сначала рассказывает теоритическую базу об концепции, подкрепляешь ссылками текущую информацию из запроса

- Разрешаю в запросе ссылаться на ресурсы которые содержат код и псевдокод
- Запрещаю подробно описывать алгоритм, если об этом сам не попросил
- Для каждой концепции генерируй диаграммы, для большей наглядности.
- Следованию стандартизированным правила создания диаграмм - диаграмм классов, последовательности, состояний и т.д. - можно пренебрегать, если это улучшит понимание данной концепции
- В финальных штрихах объяснения концепции должна создавать псевдокод.

# Работа с git-репозиторием
- Для каждой отдельной полноценной реализации концепции или функциональности, если концепция слишком сложная выделяй одну ветку. Например: добавить прыжек
- Как только фича была сделана и подтвердила ее работоспособность с моей стороны коммить ее в ветку и пуш в мою ветку
- Если фича не была полностью сделанная и не подтвердила работоспособность с моей стороны, просто коммить ее. Если я дал разрешение на коммит этого решения
- Соблюдай правила  "Conventional Commits" при именования коммитов, веток, следуй правилам описания коммита. 

# ОГРАНИЧЕНИЯ И ИНСТРУКЦИИ ДЛЯ АГЕНТА 
1. **Сначала думай:** Перед тем как писать код, кратко проанализируй задачу, предложи план из 2-3 шагов и только потом выдавай код.
2. **Не ломай существующее:** При изменении файла учитывай его текущую структуру. Не переписывай весь файл, если нужно изменить одну функцию.
4. **Ответы:** Отвечай на русском языке. Код должен быть готов к копированию без дополнительных правок.
4. **Глубокое мышление:** Размышляй также на русском языке чтобы я понимал контекст.
